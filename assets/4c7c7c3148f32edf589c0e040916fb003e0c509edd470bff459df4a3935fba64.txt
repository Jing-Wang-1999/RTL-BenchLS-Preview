    "title": "[entropy_src] Scoreboarding mispredicts SHA output in rare exception case",
    "body": "This issue describes an `entropy_src_fw_ov` test failure that is likely rare and really only appears when the test (intentionally) violates the `entropy_src` usage model.\r\n\r\nWhen in \"entropy_insert\" mode the `entropy_src` programming model requires that the application check `fw_ov_wr_fifo_full` register before deasserting `fw_ov_sha3_start`.  This prevents the initiation of SHA3 processing while the last inserted word is still in the pipeline, but not yet added to the SHA3 message.  Failure to do this check triggers an recoverable alert, and the output of the SHA3 conditioner is technically undefined,    \r\n\r\nThe last inserted word usually remains in the pipeline, outside the SHA3 engine.  In this case both the current and the following digest will be altered. (The current digest will be missing an input, and the following digest will have an extra input).   However the backpressure can clear before the SHA engine actually starts processing, in which case the usage model violation does not have any negative effects.\r\n\r\nHowever scoreboarding currently attempts to keep the simulation running by assuming that the SHA3 outputs are briefly corrupted, by the misplacement of the input data. (Short of monitoring more internal signals such as SHA3 ports, or the `main_sm` state, there is no way to detect whether corruption actually occurs).   This however leads to test failures in cases when where the usage violation causes no corruption.\r\n\r\nIn such cases the DUT is behaving exactly as currently specified: an alert is logged, yet the output is corrupted (with as much as 64 less bits of entropy in the first output, and up to 64 extra bits of entropy in the following output).  There are two ways to handle this.\r\n1.)  If this behavior is deemed acceptable, then a DV fix is in order to simply note that the corrupted outputs may be mispredicted. \r\n2.)  One could also make an RTL fix to suppress the output of corrupted words.  DV would then only need to note the corruption and anticipate that the output is discarded.\r\n\r\nThe priority of this fix probably depends on the desired course of action.  If it is deemed that an fix is required for this firmware exception case it should probably be labeled as P1, however if only a DV fix is required this rare care (at most once in 50 runs) likely will not impact nightly regressions much and can be treated as P2.\r\n\r\nLabelling this issue as P1 until a course of action is decided.",
